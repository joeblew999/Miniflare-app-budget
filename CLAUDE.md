# CLAUDE.md

Conventions for working in this repo: Baht & Dollar Budget, a contract-first app on Cloudflare Workers.

## Stack

| Layer | What | Where |
|---|---|---|
| API contract | oRPC v2 **beta** (`@orpc/*` pinned to `2.0.0-beta.43`), Zod 4 schemas | `shared/contract.ts`, `shared/schema.ts` |
| API server | `implement(contract)` in a Cloudflare Worker: RPC at `/api/rpc`, the same procedures as REST at `/api/*`, OpenAPI spec at `/api/spec.json`, Scalar docs at `/api/docs` | `worker/router.ts`, `worker/index.ts` |
| Auth | Better Auth (email + password, cookie sessions) at `/api/auth/*`; guest sign-in (anonymous plugin) in Previews and local dev only | `worker/auth.ts`, `src/lib/auth-client.ts` |
| Database | Cloudflare D1 with Drizzle ORM; SQL migrations generated by drizzle-kit, applied by wrangler | `worker/db/schema.ts`, `migrations/` |
| Front end | React 19, Vite, Tailwind v4, shadcn/ui; TanStack Query via `@orpc/tanstack-query` | `src/` |
| Build and dev | `@cloudflare/vite-plugin` builds and runs the app and Worker together in workerd | `vite.config.ts`, `wrangler.jsonc` |
| Tests | Vitest inside workerd (`@cloudflare/vitest-plugin`), real D1 with migrations applied | `worker/test/`, `shared/*.test.ts` |
| Tooling | TypeScript CLI (commander), run by Node 24 directly | `cli/` |

**oRPC is v2 beta. What models learned about oRPC is v1 and wrong for v2.** Before changing the contract, the router or the client, load the vendored skills in `.claude/skills/` (`orpc`, `orpc-contract`, `orpc-openapi`). They point to the v2 docs (`https://orpc.dev/llms.txt`; add `.md` to any docs URL). Keep every `@orpc/*` package on the same exact version.

## Three files, three jobs

| File | Holds | Never holds |
|---|---|---|
| `mise.toml` | Tool versions only (`[tools]`: node, fnox from its GitHub release) | Tasks, env vars, secrets |
| `package.json` | The goals you run, as `noun:verb` npm scripts, and the order of steps (Wireit `dependencies`, `files`) | Secrets, code |
| `fnox.toml` | Names of secrets and env vars the project needs | Real secret values |

- Each person keeps their own secret values in their own store (keychain, 1Password, age…), wired up in `fnox.local.toml`, which is gitignored. Values that reach Cloudflare belong under `[profiles.production]`.
- The CLI runs commands through `fnox exec` when they need secrets (the `secrets` option in `cli/run.ts`). In local dev and tests, wrangler passes them on to the Worker because the CLI sets `CLOUDFLARE_INCLUDE_PROCESS_ENV=true`. Only secrets listed in `wrangler.jsonc` → `secrets.required` get through.
- The `BETTER_AUTH_SECRET` default in `fnox.toml` is for local dev and tests only. `worker:ci` (used by `worker:deploy` too) refuses to deploy with it.
- Do not add `[tasks]` or `[env]` to `mise.toml`, and do not add `.env` or `.dev.vars` files.

## Commands: goals and steps

Every command is a subcommand of the project CLI, a TypeScript program in `cli/` that Node runs directly (type stripping, so no build step and no tsx). The noun is the thing being acted on, like a tag; use the existing nouns before inventing a new one.

**Nobody remembers an order.** [Wireit](https://github.com/google/wireit) runs the commands: each one declares in `package.json` → `wireit` what it needs first (`dependencies`) and what it reads (`files`). Run a goal and Wireit runs its steps first, in order, each once, and skips any step whose files haven't changed since it last passed. Each CLI command does one thing; the order lives only in the Wireit config.

**Goals** are the npm scripts you run (`npm run <goal>`). **Steps** live only in the `wireit` section and run as part of a goal. Any command also runs on its own, without what it depends on, with `npm run cli -- <noun> <verb>`.

Every command, with what it runs first, is in [docs/commands.md](docs/commands.md), generated from `package.json` and the CLI:

@docs/commands.md

Rules:
- Never write "run X, then Y" in docs or code. If a command needs another first, add it to its Wireit `dependencies`. Give a step `files` (and `"output": []` if it writes nothing) so it's skipped when nothing changed; leave `files` off a step that must always run.
- A CLI command does one thing and doesn't call other commands. Chaining is Wireit's job.
- Every CLI command is a goal or a step in `package.json`, grouped by noun. `docs:gen` fails on one that isn't wired in.
- No `scripts/` folder and no loose `.js`/`.mjs` tooling. Tooling is a command in `cli/commands/<noun>.ts`, registered in `cli/main.ts`.
- Script names are `noun:verb` and match the CLI path (`app:build` → `cli/main.ts app build`). No bare names (`dev`, `build`, `start`).
- Reuse short verbs across nouns: `dev`, `check`, `verify`, `build`, `preview`, `lint`, `smoke`, `setup`, `status`, `logs`, `types`, `deploy`, `ci`, `gen`, `migrate`, `run`, `watch`, `add`, `show`, `set`, `list`, `artifact`.
- Never list commands by hand, in any doc. `docs/commands.md` is the only list, generated by the `docs:gen` step (part of `app:verify`) from `package.json` and the CLI's descriptions; link to it instead. To change what it says, change the command's description in `cli/commands/<noun>.ts`. The same step fails if any file mentions a command that doesn't exist (`plans/` excepted).
- Every command prints timings to stderr: each tool it runs (tsc, vite, wrangler…) and its total, including on failure. They come from Commander's `preAction` hook in `cli/main.ts` and `logTiming` in `cli/run.ts`. Set `BUDGET_TIMINGS=0` to hide them.
- Pass arguments after `--`: `npm run db:gen -- add-notes`, `npm run app:smoke -- --url <url>`.
- The Wireit extension for VS Code (`google.wireit`, in `.vscode/extensions.json`) checks the config as you edit it. `npm run app:setup` installs it.

## Folder layout

```
artifact/       glue for `app:artifact`: an oRPC link that calls the router in the page, D1 on sql.js, a cookie jar for Better Auth. No app logic
cli/            project CLI: main.ts, program.ts (all commands), run.ts, commands/<noun>.ts (docs.ts writes docs/commands.md); smoke.ts (HTTP checks of a running app); browser-checks.ts (Playwright checks: the artifact build, and offline use); cloudflare.ts (REST client), cloud.ts (setup/build/status/logs), project.ts (reads wrangler.jsonc, git remote)
shared/         runtime-neutral code used by both src/ and worker/
  schema.ts         Zod schemas: the shape of a budget (types are inferred from these)
  contract.ts       oRPC contract: procedures, inputs, outputs, errors, REST routes
  budget.ts         domain maths (conversion, frequencies, formatting)
worker/         Cloudflare Worker
  index.ts          routing: /api/auth, /api/rpc, /api/* REST + docs, else static assets
  router.ts         implement(contract): procedures + auth middleware
  auth.ts           Better Auth setup
  budget-store.ts   D1 reads and writes for a budget
  db/               Drizzle schema and client
  test/             Vitest tests (run in workerd)
migrations/     SQL migrations (generated by db:gen, applied by the db:migrate step and by deploys). Never edit applied ones.
src/            React app
  App.tsx           sign-in gate, then the budget
  components/       app components; components/ui/ is managed by the shadcn CLI
  hooks/            use-budget.ts: load and autosave through the API
  lib/              api.ts (oRPC client), link.ts (where API calls go), auth-client.ts, theme.ts, storage.ts, utils.ts
  styles/           index.css (base preset), themes.css + themes.json (generated)
.claude/skills/ vendored agent skills (oRPC)
docs/           commands.md: every command, generated (never edit)
plans/          plans, named YYYY-MM-DD-NN-slug.md with the file's own name on the first line
```

- `shared/` must stay runtime-neutral, with no DOM, no `localStorage`, no Worker bindings and no Node APIs. The type-check enforces this, because `shared/` is compiled under both the app and the Worker tsconfigs.
- TypeScript is strict everywhere, with one tsconfig per runtime: `tsconfig.app.json` (src + shared, DOM), `tsconfig.worker.json` (worker + shared, Workers types), and `tsconfig.node.json` (configs + cli, Node). The `app:check` step (part of `npm run app:verify`) checks all three.
- `worker-configuration.d.ts` is generated by the `worker:types` step (vars typed as `string`, because Previews override them). It regenerates by itself when `wrangler.jsonc` changes.

## Changing the API

1. Change the Zod schema or the contract in `shared/`. The contract is the source of truth, and every procedure needs `.output` and an `openapi()` route.
2. Implement it in `worker/router.ts` (and `worker/budget-store.ts` for data). TypeScript fails until the implementation matches the contract.
3. Database change: edit `worker/db/schema.ts`, then run `npm run db:gen -- <name>`. `app:dev` applies it locally.
4. Use it in the app through `orpc` from `src/lib/api.ts` (`orpc.x.y.queryOptions()` / `.mutationOptions()`).
5. Add or extend a test in `worker/test/`, then run `npm run app:verify`.

Procedures that need a signed-in user use the `authed` base in the contract (it declares `UNAUTHORIZED`) and `authed` in the router (the `requireUser` middleware). Every query filters by `context.user.id`.

## Theme (shadcn)

- The base theme is an official shadcn preset (`npm run theme:show`). Change it with `theme:set`. Never hand-edit colour variables in `src/styles/index.css`.
- `src/styles/themes.css` and `src/styles/themes.json` are generated by `theme:set` (or on their own with `npm run theme:gen`): one block per official accent theme, built by running `shadcn init --preset` for each. Don't edit them by hand.
- Runtime switching (light/dark/system plus accent) lives in `src/lib/theme.ts` and `src/components/theme-switcher.tsx`, and uses `.dark` and `<html data-accent="…">`. The boot script in `index.html` mirrors `applyTheme()` so there's no flash. Keep the two in step.
- `src/components/ui/` is managed by the shadcn CLI (`ui:add`, `theme:set`) and excluded from lint. Put app components in `src/components/`.

## Deploying

Production deploys come from **Cloudflare Workers Builds**: Cloudflare builds the repo on every push to `main`, and every other branch gets a Preview. **Deploying is a git push.**

- **One-time setup is `npm run worker:setup`** (Cloudflare REST API, credentials from the fnox `production` profile). It creates or updates the Worker, its workers.dev URL, the staging D1 database (and writes its id into both wrangler files; commit them), a build token from your own API token, the Workers Builds connection to this repo, Previews, and random values for missing secrets, which are never printed. It is safe to re-run. `--rotate-secrets` replaces the secrets.
- `npm run worker:build` starts and waits for a production build (`-- --branch <name>` builds that branch's Preview) and prints the URL, or the log tail if it fails. `worker:status` lists the URLs and recent builds. `worker:logs` prints a build log.
- Don't set Cloudflare up by hand or through the dashboard. If something is missing, add it to `worker:setup` so it stays repeatable.

- Build command: `npm run app:build`. Deploy command: `npm run worker:ci`. Builds use Node 24, the same as `mise.toml`.
- `worker:ci` migrates D1 (`migrations/`), then runs `wrangler deploy` with the secrets from the build environment (`--secrets-file`, a temporary file that is deleted afterwards). On the very first deploy it deploys first, so wrangler creates the database, and then migrates.
- `wrangler.jsonc` has no `database_id`. Automatic provisioning creates and links the database, so the repo holds no account-specific ids. Don't add one back.
- The secrets in `secrets.required` must be set as build secrets in the Worker's **Settings > Build > Variables and secrets**. Their names are listed in `fnox.toml`.
- **Previews**: every non-production branch gets its own Preview URL. The preview command is `npm run worker:preview`: it migrates the shared staging database (`previews.d1_databases` in `wrangler.jsonc`, migrated through `wrangler.preview-migrations.jsonc`), then runs `wrangler preview` with secrets from the preview build variables. Previews never touch production data. Keep the two staging-database entries in step.
- **Guest sign-in** (Better Auth anonymous plugin) is how you get into a Preview without an account. It is on when the Worker var `GUEST_SIGN_IN` is `"true"` (set in `previews.vars`), or when the host is `localhost`. It is off in production (`vars.GUEST_SIGN_IN` is `"false"`), where `/api/auth/sign-in/anonymous` returns 404. Never set it to `"true"` for production. The app reads `GET /api/config` to decide whether to show the button.
- `npm run worker:deploy` runs the same `worker:ci` step from your machine, with credentials and secrets from your fnox `production` profile.
- Migrations must be backwards-compatible with the code that is still running, because they apply before the new code goes live. Add columns and tables first, and remove old ones in a later release.

## Showing the app in a Claude artifact

An artifact can't reach any server (local or Cloudflare), so `npm run app:artifact` builds the real app **and the real Worker** into one HTML file, `dist/artifact/index.html`. The build swaps one file, `src/lib/link.ts` (an `RPCLink` to `/api/rpc`), for `artifact/link.ts`, which calls the real router in the page with `createRouterClient` and the same `createContext` as the Worker (`worker/context.ts`). `artifact/in-page-worker.ts` provides D1 as SQLite (sql.js, set up from `migrations/`, kept in the browser's localStorage) and answers Better Auth's `/api/auth/*` requests with `worker/index.ts`. Guest sign-in is on, and nothing leaves the page. `app:artifact` then checks the file in a real browser with every network request blocked (guest sign-in, edit, save, reload), the way the artifact viewer runs it; `-- --no-check` skips that. Publish the file only after the check passes. The check uses `playwright-core` (pinned) with Playwright's Chromium (`npm run app:setup` installs it), or Google Chrome. Keep `artifact/` to glue only: app and API changes go in `src/`, `shared/` and `worker/` as usual, and the artifact picks them up on the next build.

## Verifying a deploy

After a push, check the deployed copy with `npm run app:smoke -- --url <url>`. On production it runs read-only checks (page, deep links, health, 401 without a session, spec and docs, guest sign-in closed). On a Preview or local dev it also signs in as a throwaway guest and saves and loads a budget, which only touches the staging or local database. Preview URLs are `https://<branch>-baht-dollar-budget.gedw99.workers.dev`.

Add `--offline` on a Preview or `app:preview` (not `app:dev`, which has no service worker) to check offline use in a browser: edit offline, reload with no connection, reconnect and sync, and an older offline edit losing to a newer save from another device.

## Offline

The app works offline. Change these parts together:
- `vite.config.ts`: the service worker (vite-plugin-pwa) keeps the built app in the browser. It never caches `/api/*`. It is not in the artifact build.
- `src/App.tsx`: when the session can't be checked (offline), the last signed-in user is used. Sign-in only shows when the server says there's no session.
- `src/hooks/use-budget.ts` and `src/lib/storage.ts`: each user's last server copy and an outbox of unsent edits, in localStorage. Edits go to the outbox first, then to the server when online.
- Exchange rate: always live, from `rate.get` (`worker/rate.ts`: ECB rate via frankfurter.dev, cached an hour at the edge). There is no manual rate. The budget keeps the last live rate, which is what's used offline.
- Latest edit wins: `budget.save` takes `editedAt`, and the server doesn't apply an edit older than the saved budget (`applied: false`); the app then loads the newer one. `budget.get` returns `savedAt`.

## Git

- Work on a branch and open a PR. Never push to `main`. Keep the PR mergeable, because the owner's local clone tracks the same code.
- Before pushing, run `npm run app:verify`.
