# 2026-10-16-01-secrets-push-and-broker.md

**Status:** planned. To be built on the Mac (it needs the real secrets in fnox).

## How we work on this (Mac and cloud agent)

- **Branch:** `secrets-push`, created from the latest `main`:
  ```
  git checkout main && git pull
  git checkout -b secrets-push
  ```
- Never commit to `main` directly. Merging to `main` deploys production.
- Push the branch whenever you like. Every push gets its own Preview URL. When it's done, open a PR into `main` and merge it.
- **Sync goes through GitHub.** Whoever wants the other's work pulls the branch: `git fetch && git checkout secrets-push && git pull`.
- **One writer per branch at a time.** While the Mac is working on `secrets-push`, the cloud agent stays off it, or works on its own branch (for example `secrets-push-agent`) and opens a PR **into `secrets-push`**, not into `main`.
- To hand over, push first and then say which branch to pick up.

## Problem

Every secret lives in fnox on the Mac, which is the only source of truth. Three other places need some of them and can't reach the Mac:

| Consumer | Needs | Lifetime |
|---|---|---|
| Cloudflare | Worker runtime secrets (e.g. `BETTER_AUTH_SECRET`), Workers Builds build variables | permanent |
| GitHub | Actions secrets, for any workflow that needs them | permanent |
| Cloud agent sessions (Claude) | a Cloudflare API token to deploy directly (about 30s instead of about 2 min through Workers Builds), now and then | one session, and every session starts empty |

Today these are copied by hand or not at all, so things drift, deploys are slower than they need to be, and agents get stuck.

## Principles

1. **The Mac (fnox) stays the single source of truth.** Nothing is edited anywhere else.
2. **Permanent consumers get pushed copies.** One command makes Cloudflare and GitHub match fnox.
3. **Agents never hold long-lived secrets.** They get short-lived, narrowly scoped child credentials minted from a parent token (fnox calls these *leases*).
4. **The parent token never leaves trusted storage**: the Mac keychain or 1Password, plus one GitHub Actions secret it's pushed to. It never goes into a chat, a sandbox or a repo file.

## Part 1: `env:push`, from Mac to Cloudflare and GitHub

New CLI commands in this repo, following the `noun:verb` rules in `CLAUDE.md`:

- `npm run env:push`: reads secrets through `fnox exec --profile production` and writes each one to its targets.
  - `--dry-run`: lists what would be set where, by name only and never values.
  - `--only <NAME>`: push one secret.
- `npm run env:status`: lists, by name only, which secrets exist at each target and which are missing or extra.

**Where each secret goes** is declared in a new file `env.targets.jsonc`. It's separate from `fnox.toml`, because fnox may reject unknown keys; check that and fold it in if fnox allows. Example:

```jsonc
{
  "BETTER_AUTH_SECRET": ["cloudflare:worker", "cloudflare:builds:production"],
  "BETTER_AUTH_SECRET_PREVIEW": [{ "target": "cloudflare:builds:previews", "as": "BETTER_AUTH_SECRET" }],
  "CLOUDFLARE_PARENT_TOKEN": ["github:actions"],
  "CLOUDFLARE_ACCOUNT_ID": ["github:actions"]
}
```

Targets to implement:

| Target | How | API |
|---|---|---|
| `cloudflare:worker` | Worker runtime secret | `PUT /accounts/{id}/workers/scripts/{name}/secrets` |
| `cloudflare:builds:production` | Workers Builds production build variable (`is_secret: true`) | `PATCH /accounts/{id}/builds/workers/{tag}`, `production_settings.environment_variables` |
| `cloudflare:builds:previews` | Workers Builds Previews build variable | same call, `previews_base_config.environment_variables` |
| `github:actions` | repo Actions secret | `gh secret set NAME --repo owner/repo` (value on stdin) |

Implementation notes:
- Reuse `cli/cloudflare.ts`, which already has the REST client and credentials, and `cli/project.ts`, which already knows the Worker name and the GitHub repo.
- Values go over stdin or in request bodies only, never in argv, logs or files.
- Today the production and preview `BETTER_AUTH_SECRET` values were generated by `worker:setup` and exist **only** on Cloudflare. Decide whether fnox becomes their owner. That would mean generating new values in fnox and pushing them, which signs everyone out once. The alternative is leaving `worker:setup` in charge of them.
- Add `fnox.toml` entries for each new secret, as names only, under `[profiles.production.secrets]`.

Acceptance:
- `env:push --dry-run` lists every target and touches nothing.
- `env:push` followed by `env:status` shows nothing missing.
- Rotating one value in fnox and running `env:push --only X` updates only X.

## Part 2: short-lived Cloudflare tokens for agent sessions

### What was found today

- The cloud sandbox **can** reach `api.cloudflare.com`. Direct `wrangler deploy` works from there with a token.
- The Cloudflare connector **cannot** create API tokens (error 9109), so it can't mint them.
- The session's GitHub token is a **proxy placeholder** (`prox…`): the session's proxy swaps in the real credential only on requests to GitHub. So the agent can't prove its GitHub identity to a third-party service such as a custom broker Worker. It **can** use the `gh` CLI and the GitHub API normally, including triggering workflows.

### Design: GitHub Actions mints the token

Repo write access (being able to trigger a workflow) is the identity check, and Actions holds the parent token.

1. **Parent token** (Cloudflare): a user API token with the *API Tokens: Edit* permission. Its only job is creating child tokens. It's stored in fnox on the Mac and pushed by `env:push` to the GitHub Actions secret `CLOUDFLARE_PARENT_TOKEN`.
2. **Workflow** `.github/workflows/mint-cloudflare-token.yml`, run by `workflow_dispatch` with inputs:
   - `public_key`: the requesting session's one-off public key (age, X25519);
   - `ttl`: capped at 4h.

   The workflow:
   - creates a child token through `POST /user/tokens`, with `expires_on` set to now + ttl, scoped to this account and the minimum permissions: Workers Scripts Edit, D1 Edit, Workers Builds Configuration Edit, Account Settings Read;
   - encrypts the child token to `public_key` with `age`;
   - uploads the ciphertext as a short-retention workflow artifact (1 day);
   - masks everything in the logs.
3. **Agent side**: a CLI command, `npm run cf:lease` or folded into `env`, for example `env:lease`.
   - It generates an age keypair in memory or a temp file in the sandbox.
   - It runs the workflow with `gh workflow run … -f public_key=…`, waits with `gh run watch`, downloads the artifact with `gh run download`, decrypts it, and writes `CLOUDFLARE_API_TOKEN` into the sandbox's own gitignored `fnox.local.toml` (or exports it for the session).
   - From then on, `worker:deploy`, `worker:status` and the rest work directly in about 30s.
4. **fnox integration**: describe the child token as a fnox lease with the `command` backend, so `fnox lease create CLOUDFLARE_API_TOKEN` calls the same flow on any machine, and `fnox lease revoke` deletes the token early through the Cloudflare API.
5. **Cleanup**: Cloudflare's `expires_on` kills children automatically. Optionally, a scheduled workflow deletes expired `agent-*` tokens to keep the account's token list tidy.

Why not a custom broker Worker: it would need to verify the agent's GitHub identity, and the session's token is a placeholder that only works through the session's proxy. With Actions, GitHub does that check, and no extra service has to be secured.

### Before building, verify

- [ ] Can a token with *API Tokens: Edit* create a child with permissions beyond its own, or is the child capped at the parent's permissions? This decides how narrow the parent can be. Check the Cloudflare docs for creating tokens through the API.
- [ ] Do child tokens need *account-owned* tokens (`/accounts/{id}/tokens`) instead of user tokens? Account-owned is preferable, because it isn't tied to one person.
- [ ] Does `gh workflow run` plus `gh run download` work from a cloud session through the proxy? It's very likely, since `gh api` already does.
- [ ] Is the time from triggering the workflow to having the token under about 45s? If it's much slower, Workers Builds (about 2 min) may be good enough.

Acceptance:
- From a fresh cloud session: `npm run env:lease` gets a working token in under about a minute, with no human input, and `npm run worker:deploy` then deploys in about 30s.
- The token stops working after its TTL.
- No secret value appears in any log, artifact (except the age ciphertext), chat or repo file.
